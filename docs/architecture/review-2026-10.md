# Revisión de arquitectura de EcoBike

Fecha: 2 de octubre de 2026. Proyecto: `C:\Users\donat\Documents\ecobike-app`.

Este documento acompaña a la columna de arquitectura (`architecture-ecobike-platform.md`): allí están las reglas que todo el código nuevo debe cumplir; aquí está por qué, qué decisiones se cuestionaron y qué hay que corregir.

## Resumen

La base es buena: el dinero de la app (puntos, roles, canjes) ya lo decide solo el servidor y las reglas de Firestore bloquean al cliente. Los problemas están en tres zonas:

1. **Privacidad de perfiles.** Cualquier usuario registrado puede descargar la lista completa de perfiles públicos, y "ocultarme de la búsqueda" solo se aplica en la app, no en el servidor.
2. **Rendimiento del almacenamiento local.** Todos los recorridos, con cada punto GPS, se leen y reescriben enteros; en la web además se pueden perder recorridos al llenarse el espacio del navegador.
3. **Varios caminos para lo mismo.** Cinco lugares del servidor cambian puntos, siete escriben el perfil público y cuatro definen quién es admin. Cada función nueva aumenta el riesgo de que no coincidan.

## Decisiones cuestionadas

| Decisión actual | Veredicto | Por qué |
| --- | --- | --- |
| Datos locales primero (SQLite / localStorage) | Se mantiene | Permite grabar recorridos sin internet. Hay que separar resúmenes de rutas GPS (AD-6). |
| Servidor con autoridad sobre puntos y canjes | Se mantiene | Es lo que impide el fraude. Falta un único camino para mover puntos (AD-9). |
| Reglas de puntaje duplicadas en cliente y servidor | Se mantiene, vigilada | La pantalla final necesita mostrar puntos sin conexión. Ahora una prueba de paridad impide que se separen (AD-2). |
| Firebase JS SDK también en el móvil | Se mantiene por ahora | Simplifica una sola base de código. Límite: App Check real en el móvil necesitará un módulo nativo. |
| `expo-maps` en el móvil y Leaflet en la web | Se cuestiona | `expo-maps` sigue en versión alfa y no permite la flecha rotada que pediste. Alternativa: `react-native-maps`. Decisión pendiente. |
| API en Vercel con plan Hobby | Se cuestiona | El límite de 12 funciones ya se tocó, y Hobby es solo para uso no comercial; con tiendas aliadas conviene Pro. |
| Photon y Valhalla comunitarios para Eco ruta | Se cuestiona | Gratis pero sin garantía: Valhalla permite 1 petición por segundo por usuario y pide identificarse. Para crecer: servidor propio o de pago. |
| Un solo proyecto Firebase para pruebas y producción | Se acepta con riesgo | Cómodo hoy; cualquier prueba toca datos reales. Separar cuando haya más personas desarrollando. |
| Modo invitado con puntos y códigos locales | Se cuestiona | Choca con "solo el servidor decide el valor". Debe ser demostración y nunca mezclarse con una cuenta (AD-11). |

## Fallos encontrados y estado

Corregidos en esta revisión (commits `16e50e20`, `67dd26b1`):

- El panel de admin no podía editar usuarios: faltaba el `id` (todas las ediciones fallaban con error 500).
- Recorridos reales recortados por el tope diario dejaban de contar para rachas, misiones y para poder canjear.
- Recorridos rechazados por el servidor seguían contando en el teléfono.
- Un punto GPS duplicado o viejo anulaba todo un recorrido.
- La pantalla final podía prometer puntos que el servidor luego no daba.
- Se podía borrar una tienda con códigos sin usar.
- Más de 30 fallos de interfaz: el botón de mantener presionado no se reiniciaba, la búsqueda de Eco ruta se quedaba cargando, guardar una tarjeta del panel borraba lo escrito en las otras, el mapa saltaba con una ubicación tardía, entre otros.

## Seguridad: qué está bien

- Puntos, roles, canjes, tiendas y chats solo los escribe el servidor.
- Las reglas niegan todo por defecto.
- Las llamadas a la API verifican el token, incluso si fue revocado.
- Los secretos del servidor no están en el repositorio ni en la app.
- Antifraude: velocidad de bicicleta, saltos de GPS, distancia según la ruta, topes diarios y límites de canje.
- Su límite: un cliente modificado puede inventar una ruta creíble. La defensa real es App Check con verificación del dispositivo (pendiente de decisión).

## Operación

1. Orden de despliegue: primero la API en Vercel, luego reglas e índices de Firebase, luego las apps.
2. La integración continua (CI) es la compuerta: tipos, pruebas unitarias y de paridad, reglas en emulador, build web y pruebas e2e.
3. Monitoreo con Sentry en cliente y servidor; cada respuesta de la API lleva un identificador para rastrear errores.
